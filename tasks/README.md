# REA 任务拆分执行协议

## 目标

把原来的“一张长清单 + 一个长会话”，改成：

```text
一个任务 = 一个新线程 = 一份任务卡 = 一组证据 = 一份 handoff
```

这样每个线程的上下文只包含：

1. 固定执行协议（很短）。
2. 一个任务卡。
3. 该任务实际产生的输出。

不会再把 30 个任务的历史输出反复带进上下文。

## 单线程执行模板

每轮只发送下面这段，把 `<任务编号>` 替换掉：

```text
请执行 tasks/<任务编号>.md。

要求：
1. 只执行这一个任务，不读取整份 checklist，不提前执行下一任务。
2. 先读任务卡和 handoff/<前置任务>.md（若有依赖），其他文件按需读取。
3. 所有大输出落到任务卡指定路径，聊天里只汇报 ≤30 行摘要。
4. 完成后写 handoff/<任务编号>.md：状态 / 产物 / 结论 / 阻塞 / 下一任务。
5. 若验收项未满足，标记 blocked 并停止。
```

## 启动顺序

按 `tasks/INDEX.md` 顺序执行。前置未完成时不要跳跑：

```text
P0-01 → P0-02 → P0-03 → P0-04 → P0-05
→ P1-01 → P1-02 → P1-03 → P1-04 → P1-05
→ P2-01 → P2-02 → P2-03 → P2-04
→ P3-01 → P3-02 → P3-03 → P3-04 → P3-05
→ P4-01 → P4-02 → P4-03 → P4-04 → P4-05
→ P5-01 → P5-02 → P5-03
→ P6-01 → P6-02 → P6-03
```

## Token 控制规则

- 一个线程只保留一个任务卡；不要 `cat` 整份原始 checklist。
- 每轮对话摘要目标 ≤30 行；原始日志、HAR、HTML、截图说明只写文件。
- 长输出命令必须加 `head`、`tail`、`rg`、`sed -n` 或写入文件后再摘要。
- 同一任务的失败重试最多 2 次；仍失败就写 `blocked`，不要继续刷上下文。
- 任务完成后立即结束该线程；下一任务开新线程，只传 handoff。
- P6 汇总任务最后单独开一个“只读证据汇总”线程，不继承前面任务的会话历史。

## 推荐线程粒度

- P0-01 到 P0-05：可分成 3 个线程：
  1. 授权与目录：P0-01 + P0-02
  2. 配置与验证：P0-03 + P0-04
  3. 范围冻结：P0-05
- P1：每个任务一个线程（5 个）。
- P2：每个任务一个线程（4 个）。
- P3：每个任务一个线程（5 个）。
- P4：每个任务一个线程（5 个）。
- P5：每个任务一个线程（3 个）。
- P6-01/P6-02 各自独立；P6-03 由人参与的评审线程完成。

## Handoff 格式

```markdown
# <任务编号> Handoff

- 状态：done / blocked
- 完成时间：
- 产物：
- 结论：
- 已证实：
- 待验证：
- 阻塞：
- 下一任务建议：
```

## 为什么不把 30 个任务塞进一个自动化

一次性自动化会在每轮 wakeup 时重新注入任务上下文，并把历史输出不断累积。这个仓库适合“人决定何时推进 + 每任务新线程”，比单个长自动化更省 token，也更容易定位失败。
